# План: робочий магазин-прототип на Shopify (демо для портфоліо)

Мета: з теперішнього демо (головна + сторінка товару на тимчасових даних) зробити магазин, у якому можна
пройти весь шлях: каталог → товар → кошик → оплата тестовою карткою → замовлення в адмінці Shopify.
Дизайн лишається той самий. Shopify безкоштовний (dev-магазин).

Як користуватись: один крок = одна сесія. На початку сесії: «Прочитай `docs/shopify-prototype-plan.md` і
`CLAUDE.md`, зроби крок N. Нічого поза цим кроком не чіпай». Наприкінці кожного кроку: `npx nuxt typecheck`,
перевірка в браузері на 390 / 768 / 1440 px, оновити `CLAUDE.md` (розділи «Що зараз MOCK», «Дані», «Наступні
кроки»), позначити крок тут як зроблений, коміт.

## Рішення (не переглядати без Макса)

1. **Статична збірка лишається** (`nuxt generate`, GitHub Pages). Сервера Nitro немає.
   Каталог читається з Shopify під час збірки, кошик працює в браузері напряму зі Storefront API.
   Публічний токен Storefront API для цього й призначений: він видимий покупцю, нічого секретного не відкриває.
   Розділ «Цільова архітектура» в `CLAUDE.md` (cookie, серверний callback) описує бойовий магазин з LiqPay, для
   прототипу він не діє.
2. **Оплата тільки через Shopify Checkout** (перехід на `cart.checkoutUrl`). Свою форму оплати не пишемо.
3. **Поза прототипом:** LiqPay, Нова пошта, окреме оформлення для України, Admin API, вебхуки, акаунти покупців,
   пошук, витиск ініціалів. Ключі для них з `runtimeConfig` і `.env.example` прибрати на кроці 3.
4. **Жодних фейкових «успіхів»** (правило з `CLAUDE.md` лишається): «Додано» лише після відповіді Shopify,
   помилку показуємо як помилку.
5. Типи `ProductSummary`, `ProductDetail`, `Money` і ключі `useAsyncData` (`catalog:*`) не міняються. Міняється
   лише тіло функцій у `useCatalog.ts`. Якщо поле не вдається заповнити з Shopify, воно стає `null`, а блок на
   сторінці ховається.

## Крок 3. Клієнт Storefront API

**Зроблено 2026-11-18.** Запити винесено в окремий `app/utils/shopifyQueries.ts` (fragment картки, товар за
handle, товари колекції), щоб крок 4 їх лише викликав. Категорія для крихт — перша колекція товару з таблиці
в `shopifyMap.ts` (bestsellers/frontpage пропускаються), без неї — `all`. Товар без жодного відомого кольору:
`mapProductDetail` → null (404), `mapProductSummary` → null (картку не показувати). Порожні `details` ховають
блок «Details». Перевірено тимчасовою сторінкою на barrel-bag, dome-bag, croc-box-bag, bestsellers і на
штучних даних (невідомий колір, битий JSON). Пастка з контекстом Nuxt — у `CLAUDE.md`, «Відомі пастки»:
у кроці 4 кілька запитів в одній функції робити через `Promise.all`.

- `nuxt.config.ts`: `runtimeConfig.public.shopifyStoreDomain`, `shopifyStorefrontToken`, `shopifyApiVersion`
  (`2026-10`). Старі приватні ключі Shopify, LiqPay, Нової пошти прибрати звідси і з `.env.example`.
- `app/utils/shopify.ts`: одна функція `shopifyFetch<T>(query, variables)`:
  POST на `https://{domain}/api/{version}/graphql.json`, заголовок `X-Shopify-Storefront-Access-Token`.
  Кидає помилку і на HTTP-помилку, і на непорожній `errors` у тілі відповіді (GraphQL віддає 200 з помилками).
- `app/utils/shopifyMap.ts`: чисті функції з відповіді Shopify у `ProductSummary` і `ProductDetail`.
  - Колір: опція товару `Color`, значення зіставляються з `LeatherColor` за таблицею в цьому файлі.
    Невідоме значення пропускається, а не ламає сторінку.
  - Фото за кольором: `variant.image` + фото товару, у яких `altText` починається з назви кольору (без урахування
    регістру: у CSV alt виду «Burgundy Tidal Barrel Bag, front view»).
  - `details` і `dimensions`: один metafield `custom.specs` типу JSON
    (`{"details": [...], "dimensions": {...}}`, поля як у `ProductDimensions`, відсутнє = `null`).
    `dimensions` у типі стає `| null`, блок «Size & fit» і рядок розміру ховаються, якщо його немає.
  - `subtitle`: metafield `custom.subtitle`, якщо немає — порожній рядок.
- Типи відповідей Shopify — у `shared/types/shopify.ts`, не в компонентах.

Пастка: metafield не віддається через Storefront API, поки в адмінці у його визначенні не ввімкнено доступ
для Storefront. Якщо `specs` приходить `null` при заповненому полі — причина тут.

Готово, коли: тимчасова сторінка або скрипт виводить тестовий товар з кроку 0 у формі `ProductDetail`.
Сайт ще на тимчасових даних.

варіанта кошик неможливий, інші поля не мінялись. ID кошика читається й пишеться напряму в localStorage
(обгорнуто в try/catch на випадок приватного режиму), а не через `useLocalStorage`: так простіше гарантувати,
що він читається лише після монтування. Перевірено Playwright: додати → перезавантажити → інша сторінка (UA) —
лічильник той самий; ± і «Прибрати» оновлюють суму від Shopify; без мережі кнопка показує помилку.

- `app/composables/useCart.ts` на `useState`: `cart`, `count`, `pending`, `error`, `add(variantId, qty)`,
  `update(lineId, qty)`, `remove(lineId)`, `load()`.
- Мутації `cartCreate`, `cartLinesAdd`, `cartLinesUpdate`, `cartLinesRemove`, запит `cart(id)`. Перевіряти
  `userErrors` у кожній відповіді.
- ID кошика в `localStorage` (VueUse `useLocalStorage`), читати після `useMounted()`, щоб не було розбіжності
  гідратації. Якщо `cart(id)` повернув `null` (кошик оплачений або застарів) — стерти ID і почати новий.
- Сторінка товару: кнопка додає варіант вибраного кольору. Стани: звичайний, «додаємо» (`disabled`),
  «Додано» після успішної відповіді, помилка текстом під кнопкою. Варіант не в наявності → кнопка вимкнена з
  підписом. Та сама логіка в мобільній смузі знизу.
- Лічильник у шапці (після монтування).

Готово, коли: додав товар, оновив сторінку, перейшов на іншу — лічильник той самий; з вимкненою мережею
кнопка показує помилку, а не «Додано».
